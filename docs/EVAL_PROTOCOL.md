# HRAgent 评测协议

> 配套 `DESIGN.md`。本文件定义"数字怎么算"，所有实验报告必须遵循。
> **原则：宁可报一个带置信区间的诚实数字，不报一个漂亮但定义含糊的数字。**

---

## 1. 通用规则

### R1 · 每个指标必须可被第三方复算
定义写到"换个人按定义重算能得到同一个数"的程度。含糊的指标一律不用。

### R2 · 准确率旁必须并列成本
任何准确率数字必须同时给出 tokens/task 与延迟 P50/P95。
**理由**：exp1 已实测同任务 tokens 有 10× 方差，单报准确率会掩盖成本失控。

### R3 · 成对报告拦截率与误报率
风控类指标禁止只报 Recall。只报拦截率的话，"全部拦截"就是 100%。

### R4 · 比例指标一律带 95% 置信区间
Bootstrap 重采样 1000 次。n<50 时只报方向，不声称显著性。

### R5 · 配对比较用 McNemar
同一批样本上的两个配置比较，用 McNemar 检验（二分类正确性），报 p 值与翻转方向。

### R6 · 负面结果必须进报告
假设被证伪就写"被证伪"。exp1 已经这么做了，后续保持。

## 2. 指标定义

### 2.1 意图路由（Orchestrator）

| 指标 | 定义 |
|---|---|
| **Routing F1 (micro)** | 预测执行体集合 vs 标注执行体集合，按集合算 micro-F1。多意图样本按多标签计 |
| **Routing Exact** | 预测集合与标注集合**完全相等**的比例（严格口径，单列） |
| **Clarification Recall** | 标注 `needs_clarification=true` 的样本中，系统确实发起澄清的比例 |
| **误澄清率 (FCR)** | 系统发起澄清的样本中，标注为**不需要**澄清的比例 |
| **Slot Accuracy** | 标注的必需槽位中，被正确抽取的比例 |

> 只报 Routing F1 不够：把所有 query 都路由到全部执行体，F1 也不会太差。
> 所以必须并列 **Routing Exact** 与成本。

### 2.2 Text-to-SQL（`HRDataSQL`）

| 指标 | 定义 |
|---|---|
| **Valid SQL Rate** | 生成的 SQL 能被 SQLite 成功执行的比例（区分"语法错"与"逻辑错"） |
| **Execution Accuracy (EX)** | 执行结果集与 gold 结果集**等价**的比例 |
| **口径正确率** | 结果数值正确 **且** 使用的口径与数据字典一致的比例（自建指标，见下） |

**EX 等价判定规则（必须严格执行，否则数字不可比）**
1. 行顺序无关；列顺序无关 → 双方都排序后比较
2. 两边都是空结果集 → 判**对**
3. 浮点比较容差：金额类 `abs(a-b) <= 0.01`；比率类 `abs(a-b) <= 1e-4`
4. 数值型字符串与数值型视为等价（`"12.5"` == `12.5`）
5. gold 明确要求排序时（题目含"从高到低"等），顺序参与比较

**口径正确率为什么单列**
exp1 实测：模型可以输出格式完整、`end_turn`、但口径错误的答案（`10.34%` vs 正确 `12.5%`）。
EX 只看结果集，**口径错但数值碰巧对**的情况会被漏掉。故对口径敏感题（离职率、完成率、出勤率）
单独标注 gold 口径，由规则 + 人工抽检判定。

### 2.3 制度 RAG（`PolicyRAG`）

| 指标 | 定义 |
|---|---|
| **Hit Rate@k** | gold 文档片段出现在 top-k 的比例（k=1,3,5 分别报） |
| **MRR** | 首个 gold 片段的排名倒数均值 |
| **引用准确率 (Citation Precision)** | 输出引用中，**确实支撑**对应断言的比例 |
| **引用召回率 (Citation Recall)** | 需要证据的断言中，挂上了有效引用的比例 |
| **拒答准确率** | 知识库中**确实没有**答案的问题，系统正确拒答的比例 |

> 拒答准确率是防幻觉的关键，也是最容易被跳过的。必须专门构造"库里没有"的问题集。

### 2.4 人岗匹配与技能抽取（`RecruitMatch` · exp6）

**实际测的指标（与本节初版计划的差异已注明）：**

| 指标 | 定义 | 与计划的差异 |
|---|---|---|
| **技能抽取 micro/macro-F1** | **集合级**：把预测技能集与 `gold_skills` 当集合比 | 计划是 span 级 F1。实际标注就是"技能名集合"，没有 span 边界，**span 级无从算起** |
| **trap 误抽率** | 被抽出但只属 `trap_skills`（文中"了解过"）的比例 | 计划里没有，**但它是本实验唯一能分开词表匹配与真抽取的指标** |
| **NDCG@k**（k=min(10, 组内人数)） | 按岗位分组算，再对岗位取平均 | 与计划一致 |
| **全序 NDCG** | k = 组内全部 | 新增：@10 在小组里会退化成"整组"，加一个不带截断的对照 |
| **缺must 分位** | `kind=="缺must"`（relevance=0）的样本排在组内第几百分位，1.0 = 垫底 | 新增。**这是安全侧指标**：NDCG 高但缺must 没垫底，说明排序是靠"像不像"而非"够不够格" |
| **DI（4/5 法则）** | top-50% 的性别选中率之比 | 计划里没有。敏感属性随机分配且经独立性守门，所以 DI 可测 |
| **DI 置换零分布** | 打乱性别标签 2000 次重算 DI | **必须与 DI 一起报**。见下方警告 |
| **Recall@20** | — | **未采用**：匹配集每岗位只有 8~12 人，@20 没有意义 |

> **警告：DI 的 4/5 法则在 n=120、k=60 下不可直接使用。**
> 敏感属性是随机分配的，所以"无偏见"时 DI 也不等于 1 —— 它本身是个随机量。
> 实测（`results/exp6_skill_match.md`）：零假设下 DI 中位数 **0.875**、5% 分位 **0.708**，
> **P(DI < 0.8 | 无偏见) ≈ 0.199**。也就是说按 4/5 法则判"存在不利影响"，
> **在本集规模下有约 20% 的假阳性**。**DI 必须连同置换零分布一起报，否则不可解释。**

### 2.5 风控（`RiskAgent`）

| 指标 | 定义 |
|---|---|
| **各闸门 P / R / F1** | 按故障类型分别报 |
| **整体 Macro-F1** | 各类故障等权 |
| **误报率 (FPR)** | **正常样本**中被误拦的比例 —— 与 Recall 成对报告 |
| **端到端幻觉率** | 无有效证据支撑的断言数 / 总断言数 |

### 2.6 HITL / 选择性预测（`UncertaintyGate`）

| 指标 | 定义 |
|---|---|
| **Coverage** | 系统自动回答（不升级）的比例 |
| **Risk** | 该 Coverage 下答案错误的比例 |
| **AURC** | Risk-Coverage 曲线下面积，越小越好 |
| **Escalation Precision** | 被升级的样本中，确实答错的比例 |
| **Escalation Recall** | 答错的样本中，被升级的比例 |

> **必须画 Risk-Coverage 曲线，不能只报单点。**
> 阈值可调，单点数字可以通过挑阈值来美化；曲线才反映真实能力。

### 2.7 成本

| 指标 | 定义 |
|---|---|
| tokens/task | 输入+输出，报 mean 与 P95 |
| latency | 端到端，报 P50/P95 |
| ¥/task | 按网关计费折算（若无法获取单价则只报 tokens） |

## 4. 测试集冻结流程

```
1. 生成候选样本（LLM 生成 + 规则构造）
2. 人工筛选 / 修正标注（记录修正原因）
3. 切分 dev / test（dev 用于开发期调试，test 冻结）
4. 计算 SHA256，写入 eval/FROZEN.json
5. 开发期只允许读 dev；test 仅在最终评测脚本中加载
```

`eval/FROZEN.json` 格式：
```json
{
  "frozen_at": "2026-10-XX",
  "sets": {
    "intent_set": {"path": "eval/intent_set.jsonl", "sha256": "...", "n": 300, "dev": 150, "test": 150},
    "text2sql_eval": {"path": "...", "sha256": "...", "n": 200, "dev": 100, "test": 100}
  }
}
```

**纪律：任何一次改动测试集，都必须重新打 hash 并在报告中声明"测试集已变更"。**

## 7. 复现校验（"全部数字可复现"的操作化定义）

`.venv/bin/python scripts/verify_repro.py` —— 210 项，全绿才算通过。

**它做什么**：把报告里已发表的数字，从**落盘的逐条记录**独立重算，再与
`results/*.md` 里抄下来的期望值对账。期望值硬编码在 `PUBLISHED` 里并注明出处行 ——
**抄错、或报告与数据不一致，校验就会红**。这正是要防的。

**为什么不能只读 JSON**：那验证的是"文件没被手改"，不是"数字算对了"。
本项目出过三回聚合代码写错而逐条记录是对的事故（`_top_scores` 读错键、
检索项恒为常数、exp6 的 τ 选在空信号上），共同特征都是**不报错、指标看着合理**。

**边界（必须随结果一起声明，否则"可复现"是句空话）**：

| | 能否校验 | 说明 |
|---|---|---|
| 聚合是否正确 | ✅ | 逐条记录 → 指标 → 与发表数字比 |
| exp5 全链路 | ✅ 最强 | 无 LLM，**整体重跑逐格比对**，所有质量指标逐位相同 |
| bootstrap / 置换检验的**区间与 p 值** | ⚠️ 部分 | 本校验只对点估计；区间的确定性由 `selftest_metrics` / `selftest_guards` 覆盖 |
| **LLM 的生成内容** | ❌ 原理上不可 | 重跑得到不同文本。逐条记录是**证据存档**，不是可重放的中间产物 |
| 墙钟耗时 | ❌ | 机器负载相关。exp5 重跑实测 BM25 0.20→0.37ms、Rerank 688→614ms，故**显式排除并打印**，不静默跳过 |
| exp1 | ❌ | 早期探针实验，只有单一 JSON、无逐条记录 |

对含 LLM 的实验，"可复现"的准确含义是：
**给定同一批逐条记录，所有发表数字都能重算出来。** 不要把它读成"重跑一遍结果一样"。

> 校验器**不改动它校验的对象**：exp5 重跑会写 `results/exp5_retrieval.json`
> （脚本路径写死），故比对后必须把原始字节还原 —— 否则跑一次校验就把待校验的
> 证据换成了校验自身的输出。
