# 实验 8：置信度门控的风险-覆盖曲线与 AURC

> 要回答的问题：手上这些"弱信号"（自评置信度 / 检索分 / 证据条数），
> 到底能不能把**该升级人工的样本**排到前面去？
>
> 数据：`eval/rag_eval.jsonl` 全部 **94 题**（8 条盲区 + 86 条可答）
> 原始结果：`results/exp8_raw.jsonl`（逐题）· `results/exp8_risk_coverage_all.json`
> 代码：`scripts/exp8_risk_coverage.py` · 指标：`src/hragent/metrics.py`（78 项自测）

## 结论先说

1. **融合信号确实有排序能力**：识别"会答错"的 AURC = **0.012**，基线 0.081，
   bootstrap 95% CI [0.002, 0.030] **不含基线** —— 这是本项目第一次用 AURC
   证明门控不是摆设。
2. **但增益几乎全部来自检索分，而检索分的权重是最小的那个（0.25）。**
   权重最大的两项是坏的：
   - **自评置信度（权重 0.4）方向是反的** —— 盲区题平均置信度 **0.954**，
     可答题 **0.917**。**制度没覆盖时模型反而更自信。**
   - **证据条数（权重 0.35）从不触发，且作为信号方向也是反的** ——
     实测 `n_evidence == 0` 的样本 **0/94**，这个项一次都没生效；
     而盲区题平均引用 **4.75** 条、可答题 **2.26** 条（它在列检索到的片段
     说明都不相关），所以它越高反而越该升级。
3. **排序能力 ≠ 阈值可用性。** 融合分被压缩在 0.7~1.0 的窄带里：
   阈值 0.9 时升级 93.6%、精准度 **0.091**（= 基础率 8.5%），
   即**等于"全部升级"**。要拿它做 HITL，必须在校准集上定阈值，
   不能直接写 0.5。
4. **盲区题 8/8 全部正确拒答**（说"制度中没有相关规定"并列出检索到的片段
   说明它们都不相关）。行为是对的 —— 但它是**自信地**做对的，所以
   自评置信度帮不上忙。
5. 实验过程中修掉 **一个真 bug**：`UncertaintyGate` 的检索项在 BM25 分上
   **恒等于 0**（见第六节），修好后这一项才真正开始工作。

## 一、两个升级触发条件是两回事

必须分开测，因为它们的标签性质完全不同：

| | 触发条件 | 标签 | 标签是否与检索分共线 |
|---|---|---|---|
| **分析一** | 「制度没覆盖」→ 该升级而不是硬答 | 盲区题（`gold_chunk_ids` 为空） | **否** —— P1 实测盲区题分数落在可答题区间内（8/8 超过可答题最低分），所以这是个真问题 |
| **分析二** | 「会答错」→ 该升级 | 检索失败（金标不在 top-5） | **部分共线** —— 见第五节披露 |

四条对照臂，缺一不可：

| 臂 | 含义 |
|---|---|
| **S0 无门控** | 零知识基线 = 基础风险（无信息排序的理论值） |
| **S1 自评置信度** | 执行体自报 `CONFIDENCE:` |
| **S2 检索最高分** | BM25 top-1 分 |
| **S3 证据条数** | 引用条数（归一化到 5） |
| **S4 融合** | `1 - UncertaintyGate.risk_score()` |
| **Oracle** | 完美排序 = AURC 理论下界 |

## 二、诊断先行：每个信号朝哪边？

**这一节是本实验最重要的部分**，因为它解释了后面所有曲线为什么长这样。

| 信号 | 可答题均值 | 盲区题均值 | 方向 |
|---|---|---|---|
| S1 自评置信度 | 0.917 | **0.954** | ❌ **反向** |
| S2 检索最高分 | 30.87 | 17.16 | ✅ 同向 |
| S3 证据条数 | 2.26 | **4.75** | ❌ **反向** |
| S4 融合 | — | — | ✅ 同向（但被前两项拖累） |

```
n_evidence == 0 的样本：0/94
→ UncertaintyGate 里权重最大的 +0.35「无证据」项从不触发
```

**为什么盲区题反而更自信、引用更多？** 看真实答案就明白了：

> 问：公司的期权分几年归属？
> 答：**制度中没有相关规定。** 检索到的片段仅涉及知识产权归属与年休假，
> 均未涉及期权归属年限的任何内容：- 知识产权归属方面：… [confidentiality_policy#4.1] …

模型把**所有检索到的片段都列出来**，逐条说明"它们都不相关"。这是**正确的展示依据
行为**，但副作用是：它引用的片段数（4.75）比正常答题（2.26）还多，
而且语气笃定（"制度中没有相关规定"是个很确定的陈述）→ 置信度 0.95+。

**所以 `UncertaintyGate` 的权重分配是错的**：占 0.75 权重的两项一个反向、
一个从不触发；真正有用的检索分只占 0.25。

## 三、分析一：能否识别「制度没覆盖」

n=94（盲区 8 条），**基础风险 0.085**

| 信号 | AURC | 95% CI | 风险@80%覆盖 | vs 基线 |
|---|---|---|---|---|
| S0 无门控（零知识基线） | 0.085 | — | 0.085 | ← 无排序能力 |
| S1 自评置信度 | 0.059 | [0.038, 0.186] | 0.111 | −0.026（CI 含基线，**不显著**） |
| **S2 检索最高分** | **0.018** | **[0.004, 0.041]** | 0.042 | **−0.067 ✅** |
| S3 证据条数 | 0.159 | [0.086, 0.322] | 0.111 | **+0.074 ⚠️ 比不用还差** |
| S4 融合 | 0.036 | [0.011, 0.070] | 0.083 | **−0.049 ✅** |
| Oracle 完美排序 | 0.004 | [0.001, 0.012] | 0.000 | −0.081 |

> 基线校验：随机排序 200 次均值 = **0.081**，与基础风险 0.085 吻合。

**读法：**
- **检索分能识别盲区**（CI 不含基线）—— 但这**不等于**"能卡一个阈值"，
  见第四节。
- **自评置信度不能识别盲区**，风险@80% 甚至比不用更差（0.111 > 0.085）。
- **证据条数是负资产**：AURC 0.159 ≈ 基线的两倍，方向完全反了。
  把它放进融合分是**在帮倒忙**。

## 四、排序能力 ≠ 阈值可用性（这一节消解一个表面矛盾）

P1 的结论是「检索分**无法**区分'制度里没有'和'制度里有'，任何单一阈值都会
同时造成大量误拒与漏拒」。exp8 的结论是「检索分**能**把盲区题排到后面」。

**两句都对，因为它们说的不是同一件事：**

| | 问的问题 | 结论 |
|---|---|---|
| P1 | 能不能卡**一个阈值**把两类分开？ | 不能 —— 分布严重重叠（盲区 12.3~27.2，可答最低 6.6，8/8 盲区题超过可答最低分） |
| exp8 | 排序**平均而言**是否优于随机？ | 能 —— AURC 0.018 vs 0.085 |

**分布重叠与排序有效可以同时成立。** 举个极端例子：两类均值差很小但方差巨大时，
排序仍显著优于随机，但任何单阈值都会切错很多。

**工程含义**：不能把"检索分低 → 升级"写成硬阈值。它只能作为**融合分的一个分量**，
由融合分在校准集上定阈值 —— 而这正是 `UncertaintyGate` 的设计意图。
问题在于权重（第二节）和校准（下面）。

### 融合分根本没有校准

| 阈值 | 自动处理率 | 升级率 | 升级精准度 | 升级召回 |
|---|---|---|---|---|
| 0.3 | 1.000 | 0.000 | — | 0.000 |
| 0.5 | 1.000 | 0.000 | — | 0.000 |
| 0.7 | 0.979 | 0.021 | 0.000 | 0.000 |
| 0.8 | 0.936 | 0.064 | 0.000 | 0.000 |
| 0.9 | 0.064 | **0.936** | **0.091** | 1.000 |

融合分挤在 0.7~1.0：阈值 ≤0.6 时**一条都不升级**，≥0.9 时**几乎全升级**，
而全升级的精准度 0.091 恰好等于基础率 8.5% —— 即**没有任何判别力**。

**`UncertaintyGate(threshold=0.5)` 这个默认值在本数据上等于"门控关闭"。**
这不是阈值选错了，是**分数没有校准**（各项权重与量纲都是拍脑袋定的）。
要做 HITL，必须留一个校准集专门定阈值。

## 五、分析二：能否识别「会答错」

n=86（检索失败 7 条），**基础风险 0.081**

| 信号 | AURC | 95% CI | 风险@80%覆盖 | vs 基线 |
|---|---|---|---|---|
| S0 无门控 | 0.081 | — | 0.081 | ← 无排序能力 |
| S1 自评置信度 | 0.032 | [0.007, 0.085] | 0.076 | −0.049（CI 上界贴基线，边缘） |
| S2 检索最高分 | 0.019 | [0.004, 0.045] | 0.015 | −0.063 ✅ |
| S3 证据条数 | 0.168 | [0.063, 0.301] | 0.106 | **+0.086 ⚠️ 更差** |
| **S4 融合** | **0.012** | **[0.002, 0.030]** | 0.030 | **−0.069 ✅** |
| Oracle | 0.004 | [0.001, 0.010] | 0.000 | −0.078 |

> 基线校验：随机排序 200 次均值 = **0.077**。

**这是融合唯一真正体现价值的地方**：S4（0.012）优于任一单信号
（S1 0.032、S2 0.019），说明**融合本身带来了单信号没有的信息**。
代价是它同时继承了 S3 的负资产 —— 如果去掉 S3 项，融合分应该更好。

**共线披露**：本分析的标签是"金标是否被检索到"，而 S2 就是检索分。
两者关系密切但不等价（高分不保证金标在 top-5 内），所以这不是纯循环论证，
但**存在部分自我指涉**。因此本报告的**主要结论以分析一为准** ——
分析一的标签（制度有没有覆盖）完全不是从检索推导出来的。

### 标签效度审计（必须做，因为标签错了结论就全错）

`rag_eval` 只标了 `gold_chunk_ids`，没有金标答案文本，所以"答对"只能用引用判定。

**审计 1：L1（检索命中）与 L2（引用命中）在这 86 条上逐条完全一致（0/86 不一致）。**
说明"检索不到就引不到"，引用判据不提供额外信息。保留 L2 只是为了把
"这两个标签在本数据上等价"这件事**测出来**，而不是假定它们不同。

**审计 2：人工逐条看 7 条判为"错"的可答题，发现它们全部是检索失败**
（金标片段不在 top-5），且其中：

| 类型 | 条数 | 说明 |
|---|---|---|
| 模型仍靠其他片段**答对** | **3** | 如"加班工资几倍"引 `attendance_policy#3.4`（写了 150/200/300%）而非金标 `labor_law_excerpt#2.3` —— **答案是对的** |
| 退化成**错误拒答** | **4** | 说"制度中没有相关规定"，而金标存在 |

→ **「检索失败率 8.1%」是确定性、可审计的指标；有效答错率是 4/86 = 4.7%。**
报告同时给出两者，不把检索失败率说成答错率。

## 六、过程中修掉的真 bug：检索项恒等于 0

**这是 exp8 跑通之前发现的，不修则本实验的全部结论都不成立。**

`UncertaintyGate` 第一版：

```python
scores = (c.artifacts or {}).get("top_scores") or []
if scores:
    # 检索分低 → 更可能制度里没有。归一化到 [0,1]（bge 余弦区间）
    top = float(scores[0])
    s += 0.25 * (1.0 - max(0.0, min(1.0, top)))
```

注释写的是"归一化到 [0,1]（bge 余弦区间）"，但 `retrieval.index()` 返回的是
**BM25 分**（`idf·tf·(k1+1)/(tf+k1·(1-b+b·len/avg_len))`），**无上界**。实测：

```
94 题的 BM25 最高分：min 6.58 / p25 18.43 / 中位 27.46 / p75 36.42 / max 99.82
→ `1 - min(1, top)` 恒为 0 的样本：94/94 = 100%
```

**检索项对 94/94 条样本的贡献恰好是 0。** 与 `_top_scores()` 读错键是同一类毛病：
信号静默失效、不报错、任何指标都不变。

**修法**：饱和式归一化 `conf = top / (top + MID)`，`MID = 27.0`
（94 题 BM25 最高分的中位数）。选饱和式而不是 `min(1, top/P90)`：
处处可导、不产生"卡在阈值上的平台区"、只需一个**量纲常数**。
MID 是**索引的量纲属性**（由冻结的 `policy_chunks` 语料决定），不是标签信息，
不构成对评测集的调参。

回归测试固化在 `scripts/selftest_guards.py` 第 [14] 组。

## 七、方法论：基线被数据顺序伪装成了好成绩

第一版把"无门控"臂实现成**常数置信度** `[1.0]*n`。结果 S0 的 AURC 算出 **0.004**，
而真实基础风险是 **0.085** —— 基线看起来比任何信号都好。

原因：`risk_coverage_curve` 对同分样本用的是 Python 稳定排序，于是实际按
**输入顺序**取前缀。而本数据里 **8 条盲区题恰好都在文件末尾**（位置 86–93），
所以常数臂的前 86 条全是可答题、风险为 0。

**修法**：S0 臂直接用**基础风险本身**（无信息排序的理论值），
并加一个**随机排序 200 次均值**的校验臂（实测 0.081 / 0.077，与基础风险吻合）。

> 教训与 exp7 的「零知识基线」同源：**基线必须用理论值或随机化来定义，
> 不能用一个会受实现细节（这里是文件顺序）影响的构造。**
> 否则基线会随机地变好或变坏，整个对照失去意义。

## 八、对设计的影响

1. **`UncertaintyGate` 的权重要重定**，且不能拍脑袋：占 0.75 权重的两项
   （自评置信度、证据条数）在本数据上方向是反的。**建议的下一步是
   在 dev 划分上拟合权重，在 test 上验证** —— 这正是本实验暴露出的缺口。
2. **证据条数这一项应当移除或反向使用。** 它的物理含义被搞反了：
   引用多不代表有据，可能恰恰代表"检索到的东西都不相关，只好全列出来"。
3. **融合分需要校准集。** 当前 `threshold=0.5` 等于门控关闭。
   HITL 的阈值必须在留出集上定，并且要报"升级精准度 / 召回"而不只是升级率。
4. **P1 的结论要精确表述**：不是"检索分没用"，而是
   **"检索分不能单独作为阈值判据，但作为融合分的一个分量有排序价值"**。
   exp8 给这句话提供了 AURC 层面的证据。
5. **主线结论**：门控的 AURC（0.012 vs 基线 0.081）证明
   **"用风险-覆盖曲线衡量风控"是可行且必要的** —— 单点阈值数字
   （"升级率 20%，准确率 92%"）在本数据上可以被完全打扮成假象（第四节）。

## 九、已知局限（如实记录）

1. **错误样本只有 7 条**，AURC 的点估计不稳定。已报 bootstrap 95% CI，
   但小样本下 CI 本身也粗。**本实验应重复运行**（`scripts/repeat.py`）后才能下最终结论。
2. **只有 8 条盲区题**，分析一的正类样本极少。结论方向可信，具体数值不可过度解读。
3. **单次 LLM 运行**：本实验的答案只跑了一轮，未做运行间方差量化。
   按 exp3 的教训，任何单轮 LLM 评测都不能作为最终结论。
4. **只测了 RAG 路径**（PolicyRAG）。Text-to-SQL 路径（HRDataSQL）的信号
   与标签未纳入 —— exp4 已有该路径的执行结果正确率，可作为后续补充。
5. **`rag_eval` 没有金标答案文本**，所以"答对"只能靠引用/检索判定。
   第五节已做人工审计，但这仍是标签层面的结构性限制。
